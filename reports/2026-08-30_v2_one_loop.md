# 4.1 One loop — implementation and offline evidence

**Date:** 2026-08-30
**Roadmap item:** queue 4, sub-step 4.1, approved by the human in words.
**Preparation:** `reports/2026-08-30_v2_step4_harness_preparation.md`
**Also closes:** the out-of-band control-signal requirement recorded against 4.1
after 4.0 was accepted —
`reports/2026-08-30_v2_conversation_serialization.md`, last section.

**The loop is accepted live** (see "Accepted live"), and the deployed profile
has since been **migrated and deployed** (see "Migrated and deployed"). What
remains is the one check only the real bot can make.

## What changed

**The router is gone.** `GeneralHarness.decide` spent a full-context structured
model request, before the answer the person was waiting for, to choose between
two lifecycles. There is one lifecycle now, so there is nothing to choose. A
measured turn's `route` is `loop`, and a plain conversational message costs one
model call where it used to cost two. This is the item-6 optimization, deleted
rather than implemented.

**The second lifecycle is gone.** `task_graph.py`, `task_worker.py`,
`task_validator.py`, `task_runtime.py` and `harness.py` — about 1,730 lines —
together with the adapter's act branch, Chainlit's task branch, the task
checkpoint file and setting, and their tests. What survives is
`load → model → tools → model → persist`, which was always the general loop.

**The loop gained the three things only the task path had.**

- *A spend ceiling.* `TurnBudget` bounds steps, tool calls and wall seconds; it
  is configuration (`AGENT_TURN_MAX_*`), because the right answer differs
  between a personal machine and a billed deployment. Before this, the
  conversational graph had no tool-call or time bound at all — only LangGraph's
  recursion limit, which is a guard against a graph that cannot terminate, not
  a statement about what a question may cost on a GPU billed by the second.
  Crossing a limit is not an error: no further tool runs, and the model is
  asked once more, *without tools*, for the answer the person is owed. A
  ceiling of N steps therefore costs at most N + 1 model calls.
- *Progress a person can watch.* Each pass of the loop emits a `loop_step`
  event carrying the step, the tool calls so far and the milliseconds spent;
  `tools/show_run.py` renders them as a Steps section and names the limit or
  the stop that ended a turn early. In the chat, the transient tool status now
  says which step it belongs to from the second onwards — a turn that reads one
  file is not a process anyone needs a progress report on, and a turn on its
  fifth step is.
- *A stop that works.* Below.

**Time is accumulated, not measured from the start.** Each node adds its own
elapsed to the turn's spend, so a turn that waited an hour for someone to
approve a call is not instantly over budget when they answer.

**A control signal travels out of band, and the loop acts on it.** Two separate
faults, and fixing either alone delivers nothing:

- *Delivery.* `travels_out_of_band()` in `wire.py` marks exactly the updates
  that never reach the model. The webhook writes that as `telegram_updates.control`;
  the claim never takes a control row for a conversation, and a control worker
  answers its one update and exits rather than draining the conversation. The
  local profile handles the same updates beside its per-chat lock instead of
  behind it.
- *Effect.* `app/agent/stop.py` owns `StopRequests`. The loop asks at each step
  boundary — before any tool runs and before anyone is asked to approve one —
  and a stopped turn ends with every call answered, an assistant message saying
  it stopped, and **no further model call**: someone who asked for the work to
  end is not asking to pay for one more request. `MemoryStopRequests` serves the
  local profile, which is one process. `PostgresStopRequests` serves the
  deployed one, where `/stop` is answered in one container and the turn it ends
  runs in another.

**A stop carries a sequence and cannot outlive its turn.** Every incoming event
of a conversation has a number that only grows — Telegram's `update_id`, a
session counter in Chainlit — and a stop applies to every turn that began
before it and to none that began after. That is the failure a plain boolean
flag has: an unconsumed stop cancelling the next message.

**`/stop` now says what is true.** "Stopping. Anything running will stop at its
next step." It used to claim a task had been stopped, which it could only do
for a task *paused at an approval*: `TaskRuntime.cancel` wrote a durable
outcome into a checkpoint that a graph running in another container never read.

## What it does not do

- **No consent policy change.** Workspace autonomy is 4.2's, at the tool
  execution seam. `write_file` and `edit_file` still ask.
- **No coalescing, no `todo`, no `ask_user`, no context reordering.** 4.4–4.6.
- **No proportional validation.** 4.3. This is why the verifiers went; below.

## The verifiers went with the lifecycle, and that is worth saying plainly

`app/agent/browser_verifier.py` and `app/agent/web_verifier.py` (725 lines and
their tests) were deleted. They produced the deleted lifecycle's `TestReport`
for its `evaluate` node and imported its types; keeping them would have meant
keeping a task vocabulary alive for code no product path reaches. They were
already unreachable: nothing outside `app/agent/__init__.py` and their own tests
constructed one, and no route wired them as a `Tester`. 4.3 decides what
validation the one loop does, and a resurrected HTML/browser verifier is
probably not it. Git has them if that turns out to be wrong.

## Checks

Offline suite: **707 passed, 20 skipped** (`.venv\Scripts\python.exe -m pytest
tests/ -q`), against 683 passed and 11 skipped before.

New offline tests:

- `tests/test_turn_bounds.py` (15) — a model that never stops calling tools is
  stopped; the turn still answers afterwards and its last request is offered no
  tools; the tool ceiling counts calls and the seconds ceiling counts seconds;
  one turn spends none of the next one's budget; a stop between steps ends the
  turn, runs nothing further and pays for no extra model call; a stop from
  before the turn does not stop it; one person's stop is not another's; a stop
  channel that raises does not fail the turn; and a stopped turn is a history
  the next request can be built from — every call the model made has a result.
- `tests/test_telegram_polling.py` (2) — the local profile's twin of the same
  rule: `/stop` is handled while the turn it stops is still running, and an
  ordinary second message still waits for the one before it.
- Four in `tests/test_telegram_webhook.py` — the front door marks control
  updates and nothing else; a stop is answered while the turn it stops is
  running; a control worker does not take the conversation over; a running
  control update does not hold a conversation up.
- Two in `tests/test_telegram_adapter.py` — `/stop` records a request with the
  update's own number and reaches no model; and both halves together, where a
  recorded stop ends the turn that was already running.
- Three in `tests/test_run_inspector.py` — the loop's steps are what a long turn
  is read by, and a turn that hit its ceiling or was stopped says which.

**The PostgreSQL contract suites were run against the deployed database**, on
the human's permission: **19 passed in 177 s**, both files, including all nine
new tests. They create a schema with a random name and drop it in a `finally`;
no existing table was touched and no migration was run against the `assistant`
schema. The nine new ones:

- `tests/test_update_inbox_contract.py` gained four: a control update is claimed
  while the conversation runs; it is never what a conversation claims; a running
  control update does not hold a conversation up; and the migration itself —
  the column dropped, rows written as the previous deployment wrote them,
  `setup()` run, and every row still meaning what it meant.
- `tests/test_stop_requests_contract.py` is new (5): a stop applies to
  everything that began before it and nothing after; an unstopped conversation
  is not stopped; one person's stop is not another's; a second stop never moves
  the mark backwards; setting up twice changes nothing.

**Running them found something older than this sub-step.** They errored at
fixture setup with `Psycopg cannot use the 'ProactorEventLoop'` — Python's
default event loop on Windows, which psycopg refuses to run async on. That is
not a defect in 4.0 or 4.1: it means **no live PostgreSQL test in this
repository has ever been runnable on this machine**, including the inbox
contract suite written for 4.0 and the store contract suite older than both.
`tests/conftest.py` now implements pytest-asyncio's `pytest_asyncio_loop_factories`
hook and hands the suite a selector loop on Windows, which is the same choice
`tools/setup_control_plane.py` already makes for itself. The offline suite is
unaffected: 707 passed either way.

Not run: `ruff` (configured in `pyproject.toml`, not installed here).

## Accepted live, 2026-08-30

Driven by `scripts/loop_live.py` — the loop directly, without Telegram, because
Telegram tests the transport and this is about the loop. It writes into a
temporary directory and its own SQLite telemetry: the deployed database was not
touched, and neither was the local profile's own data. One warm window, four
turns, on the human's explicit permission to wake the GPU.

| | what it asked | model calls | tools | seconds |
|---|---|---:|---|---:|
| A | an ordinary question, in Russian | **1** | — | 11.17 (the GPU wake) |
| B | read a file and quote it | 3 | `list_files`, `read_file` | 2.05 |
| C | write a file, read it back, report | 3 | `write_file`, `read_file` | 3.98 |
| D | five files, stopped mid-flight | 3 | `write_file`, `read_file`, and one refused | 3.08 |

**A is the whole point of the deletion.** One model call. Before 4.1 the same
message cost two, because the router ran first, every time, before the answer
the person was waiting for.

**C is the second point.** A request that would have gone down the act route —
plan, grant, implement, validate, evaluate, finalize — is now three steps of one
loop with one consent question in the middle, and the answer quotes the file it
had just written. No mode, no plan to approve, no lifecycle.

**D is the correction from the human, working against a real model.** The stop
was recorded while the turn was running. At its next step the loop found it: the
third `write_file` the model had just asked for was **not run**, the turn ended
with "Stopped at your request.", and no further model call was spent. The
rendered run says so in its own words:

```text
Steps
  1       0.00s spent   0 tool call(s) so far
  2       1.05s spent   1 tool call(s) so far
  3       1.88s spent   2 tool call(s) so far
  the turn was stopped by the person
```

Over the four turns `tools/show_run.py --summary` reports **2.50 model calls a
turn** against the measured baseline of 3.00, 1.50 tool calls, and a derived
$0.0045 a turn — $0.0181 for the window. That comparison is honest about only
one thing, and it is the one that matters: every one of these turns saved
exactly one router call, and A shows the saving with nothing else in it. The
scenarios are not the six live Telegram turns the 3.00 came from, so the
averages are not measuring the same workload.

**One trace artefact, not a fault:** `approval_requested` is recorded twice per
consent question. Resuming restarts the `tools` node from the top, which is
what keeps a tool from running twice, and the event is emitted again on the way
through. It predates this sub-step.

## Migrated and deployed, 2026-08-30

Both on the human's explicit permission, in that order.

**Migration.** `tools/setup_control_plane.py` against the deployed Neon
database, exit 0. Read back from the catalogue: `telegram_updates` now carries
`control boolean NOT NULL DEFAULT false`, and all **89** existing rows have it
— every one of them `false`, which is what they already meant. `turn_stops`
exists with `conversation_key`, `sequence`, `requested_at`, and is empty. No
table was dropped and no row rewritten. The schema now holds `facts`,
`messages`, `schema_version`, `telegram_updates`, `telemetry_version`,
`threads`, `trace_events`, `turn_runs`, `turn_stops`, `user_state`.

**Nothing was in flight across the deploy**: zero unfinished rows in the queue,
which is the condition the preparation asked for — a turn waiting at an
approval when the code changes under it is the risk, and there was none.

**Deploy.** `assistant-control` in 9.3 s, five functions re-created. The first
attempt failed after building every image, on `'charmap' codec can't encode
character '✓'` — Modal printing a tick into a cp1252 console, not a
deployment failure. Re-run with `PYTHONIOENCODING=utf-8`. Worth knowing: on this
machine every Modal deploy needs that, and the error it prints otherwise looks
like the deploy broke.

No GPU was touched by either step.

## What the live check found, 2026-08-30

The bot ran the two scenarios. `/new`, `plan.txt`, the apple burst and `/stop`
are all in the deployed queue and in `turn_runs`.

**One loop, in production.** Every turn is `route loop`. The rows above them in
the same listing are yesterday's: `route answer` at **2** model calls for a
plain message, and `route act` at 8 model calls and 6 tool calls for one task.
Today the same shape of work costs 1 model call to ask and 2 to do it. The
comparison is only exact on the first line — every turn saves one router call —
because the tasks are not the same task.

**`plan.txt` ran as one turn.** One consent question, then `write_file`,
`read_file` and an answer quoting the file. No "Planning...", no plan to
approve, no lifecycle. `loop_step step=2` and `step=3` are in the trace, so the
step counter works deployed.

**The control lane is live and in use.** `control = true` stands on exactly two
rows, `/new` and `/stop`, and on none of the ordinary ones. `/stop` arrived at
00:42:37.75, *while* the turn from 00:42:35.3 to 00:42:40.2 was running, and was
claimed at 00:42:41.5 — 3.75 s later, of which the cold start of a fresh
container is the whole story: `/new`, arriving with an empty queue and nothing
to wait for, paid 6.0 s for the same thing. A control row also cannot wait for a
conversation, because its claim names no conversation. What this run did not
happen to show is a claim *overlapping* a running turn; it missed by 1.3 s.

**The stop was recorded and not consumed**, because the turn it was aimed at had
already stopped at a consent question — waiting for a person, spending nothing.
`turn_stops` holds the row.

### And then the button press failed the turn

Pressing that pending consent button four and a half minutes later produced a
**failed** run with zero model calls and `TelegramError`. The queue kept the
reason:

```text
Bad Request: query is too old and response timeout expired or query ID is invalid
```

Telegram expires a callback query after a few minutes. The adapter answers the
callback *before* doing the work, `handle_update` re-raises `TelegramError` so
transport failures are retried, and the person's approval was therefore thrown
away by the failure of the spinner that told them it had been received.

**After 4.0 that is worse than one lost turn.** The failed update went back to
the queue, and a lease belongs to a conversation: the next message would claim
this update first, fail on the same expired callback, requeue it and die, for
ever. Nothing bounded the retries. The deployed bot was, at that moment, unable
to answer that person again.

Two fixes, both small:

- **`answer_callback` never raises.** It is an acknowledgement, and the project
  already holds this rule for the typing indicator, the tool status and the
  answer preview: presentation cannot fail a turn. A late press now approves the
  call it was always going to approve.
- **`MAX_ATTEMPTS = 3`, and then the queue gives up.** `abandon()` marks the row
  done with its reason kept in `last_error`, and the worker does not re-raise
  after abandoning — the point of giving up is that the conversation carries on.
  `InboxJob` now carries `attempts`, which the claim already counted.

The first fix is older than both sub-steps and would have cost one turn before
conversations had leases. The second is the invariant 4.0 needed and did not
have.

## What is still owed before this is done

- **`docs/PRODUCT.md` was deliberately left unchanged.** Two lines in it — the
  task-validation bullet and "resumable approvals and a bounded task lifecycle"
  in the accepted deployed baseline — describe what is *deployed*, and the
  deployed profile still runs the old code. They are edited when 4.1 is
  deployed and accepted live, not before.
- **Old `task:<thread>` checkpoint rows are now unreadable**, because the
  dataclasses they hold no longer exist. Nothing reads them either — no code
  path opens a `task:` thread any more — so they are dead weight rather than a
  fault. Deleting them is a destructive operation on a populated database and
  stays a separate gate.
- **A stop consumed by a turn that was actually running.** Recorded live, never
  read, because the turn had parked at a consent question. The armed stop is
  still in `turn_stops` and the pressed-but-failed callback is still pending in
  the queue, so deploying the fix above should complete both at once: the next
  worker claims that callback, the acknowledgement no longer fails, the resume
  re-enters the loop, and the loop finds the stop.
- **The deploy of the two fixes**, without which the bot cannot answer that
  person at all.
